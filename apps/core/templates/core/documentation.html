📖 What is mCube?

mCube is a sophisticated algorithmic trading system designed for the Indian stock market. It provides automated trade execution, real-time analytics, risk management, and AI-powered insights to help you make better trading decisions.

The platform integrates with major Indian brokers (Kotak Neo, ICICI Breeze) and supports multiple trading strategies including Futures trading, Nifty Strangles, and Iron Condors.

🚀 Quick Start Guide

Get up and running with mCube in minutes

1

Configure Broker Credentials

Navigate to System Configuration and enter your broker API credentials. mCube supports Kotak Neo (for Options) and ICICI Breeze (for Futures).

2

Authenticate with Brokers

Kotak Neo (v2): Go to /brokers/kotak/login/ and enter your UCC, TOTP secret, and MPIN. Authentication is fully automated using TOTP + MPIN — no manual OTP required.
ICICI Breeze: Enter your API key/secret. When the system initiates a session, you'll receive an OTP on your registered mobile — send it to the Telegram bot to complete login. One auto-login attempt per day is enforced.

3

Set Risk Parameters

Configure your risk tolerance, maximum position size, and daily loss limits. This ensures the system respects your risk boundaries.

4

Execute Your First Trade

Go to Trade → Execute Trade and use one of the available algorithms: Futures Algorithm, Nifty Strangle, or Broken Iron Condor.

Pro Tip

Start with paper trading or small positions to familiarize yourself with the system before scaling up.

✅ Trade Confirmation Flow (Futures)

Futures trades use a two-step Telegram confirmation flow managed by TradeConfirmationService (apps/trading/services/trade_confirmation.py):

  1. Selection Screen: Bot sends TOP 3 candidates with score summary and "View Details" buttons.
  2. Detail View: Full 12-factor analysis with "✅ Confirm Trade" button. Use "← Back" to return to the list.
  3. Execution: Background thread places orders (non-blocking). Orders > 10 lots are split into batches of 10 with 10-second delays.
  4. Stop Execution: A "🛑 Stop Execution" button appears during batching. Cancels remaining batches (already-placed orders are NOT reversed).

Callback patterns: select_futures_{id} (view details), confirm_futures_{id} (execute), back_futures_list (return to list), cancel_futures_exec_{id} (stop batching).

Unified Context: Both Celery tasks and web views access trading state via TradingContext (apps/core/services/trading_context.py). Use ctx = get_trading_context() — it consolidates account retrieval, trading day validation, config access, and position queries.

🧮 Strangle Strike Calculation - Step by Step

Complete formula for arriving at strike prices with a worked example:

📁 apps/strategies/services/strangle_delta_algorithm.py | apps/strategies/shared/strike_calculator.py

Step 1: Base Delta Selection

if days_to_expiry <= 2: base_delta = 0.75% # Higher delta for short expiry else: base_delta = 0.50% # Standard delta

Step 2: Apply All Multipliers (Multiplicative)

adjusted_delta = base_delta × vix_adj × trend_adj × volatility_adj × oi_adj × pcr_adj × news_adj

Step 3: Calculate Strike Distance

strike_distance = spot_price × (adjusted_delta / 100) × days_to_expiry

Step 4: Apply Asymmetric Bias (News + Technical)

call_distance = strike_distance × call_multiplier × news_call_bias × technical_call_adj put_distance = strike_distance × put_multiplier × news_put_bias × technical_put_adj

Step 5: Round to Nearest Strike

call_strike = round((spot + call_distance) / 50) × 50 put_strike = round((spot - put_distance) / 50) × 50

🧮 Iron Condor Strike Calculation - Step by Step

Complete logic for all 3 legs with a worked example:

📁 apps/strategies/strategies/kotak_broken_iron_condor.py | apps/strategies/shared/strike_calculator.py

Step 1: Calculate Strangle Strikes (Legs 1 & 2)

Uses same delta-based algorithm as Strangle strategy:

# Same as Strangle calculation strike_distance = spot × (adjusted_delta / 100) × days_to_expiry call_strike = round((spot + strike_distance) / 100) × 100 put_strike = round((spot - strike_distance) / 100) × 100

Step 2: Get Option Premiums

call_premium = fetch_option_premium(call_strike, 'CE') put_premium = fetch_option_premium(put_strike, 'PE') total_premium = call_premium + put_premium max_profit = total_premium × quantity # (lot_size = 50)

Step 3: Calculate Insurance Strike (Leg 3)

risk_budget = max_profit × risk_multiplier max_loss_per_share = risk_budget / quantity insurance_strike_raw = put_strike - max_loss_per_share insurance_strike = round(insurance_strike_raw / 100) × 100 # Safety floor: must be at least 100 points below put strike if insurance_strike >= put_strike: insurance_strike = put_strike - 100

Why "Broken" Iron Condor?

A standard Iron Condor has 4 legs with hedges on both sides. Our version is "broken" because we only hedge the put side (downside protection), keeping the call side unhedged for higher premium collection. This is ideal when you expect range-bound markets with slightly bullish bias.

🔄 How Task Scheduling Works

  1. Definition: Every task has a default schedule defined in TASK_DEFAULT_CONFIG (apps/core/task_config.py) — hour, minute, days of week, and category.
  2. Database State: The CeleryTaskState model tracks whether each task is enabled or disabled, plus any custom schedule overrides you've configured via the UI.
  3. Schedule Loading: When Celery Beat starts (or restarts), load_beat_schedule() reads the database, includes only enabled tasks, and applies any custom schedules.
  4. Runtime Safety: Every task function has a @task_enabled_guard decorator that double-checks the enabled state before executing — even if Beat fires a stale schedule.
  5. Execution Logging: Every task execution is recorded in the BkLog table with timestamp, duration, success/failure, and category. You can view these in the Celery dashboard under "Recent Executions."

📍 Support & Resistance Exit Engine

Multi-factor structural S/R engine with confidence-gated triggers and adaptive thresholds

📁 apps/positions/services/sr_exit_engine.py | sr_exit_engine_utils.py | 6 enhancement modules

🏗️ Architecture Overview

The S/R Exit Engine is the core structural intelligence layer of mCube. It computes support and resistance levels from 8 independent data sources, enriches them with multi-timeframe analysis, OI wall detection, and order block identification, then uses a two-condition SL trigger with confidence-gated rules to protect open positions.

The engine runs once per position per monitor cycle (every 1 minute during market hours). Its public API is apply_sl_and_target(position, dashboard, now), which returns a dict indicating whether a structural SL was triggered, what the reason was, and any structural pressure warnings.

💡

Key Design Principles

1. SL is only ever tightened, never loosened (LONG: higher SL = tighter; SHORT: lower SL = tighter).
2. Two conditions must BOTH be met before triggering a structural exit (price breach + session extreme confirmation).
3. All computations are fail-safe: any error returns safe defaults, never crashes the monitor cycle.
4. SL and target are propagated to sibling positions (same underlying + direction) across all brokers.

📊 8-Source Weighted S/R Computation

The MultiFactorSRCalculator aggregates support and resistance levels from 8 independent sources, each with a configurable weight. Levels within 0.3% of each other are clustered together (scores summed), producing a consolidated list of structural levels ranked by significance.

🧮 Mathematical Calculations

📐 Average True Range (ATR)

ATR measures volatility by decomposing the full range of price movement, including gaps. Used extensively for SL placement and threshold scaling.

# True Range for each bar (accounts for gaps) TR = max( High - Low, # Intraday range |High - Previous_Close|, # Gap up range |Low - Previous_Close| # Gap down range ) # ATR = simple average of TR over N periods (default 14) ATR = mean(TR[-14:]) # ATR as percentage of price (used for scaling) atr_pct = ATR / current_price

Usage: SL condition scaling, target offset interpolation, volatility event detection (body > 2x ATR), order block detection (impulse > 1.5x ATR).

📊 Volume-Weighted Average Price (VWAP)

Institutional fair-value indicator. Price above VWAP = bullish bias, below = bearish.

# Typical Price per candle TP = (High + Low + Close) / 3 # Cumulative VWAP VWAP = Σ(TP x Volume) / Σ(Volume) # Standard Deviation for bands σ = sqrt(E[TP^2] - E[TP]^2) # Band levels (used as S/R source) Upper Band 1σ = VWAP + σ Lower Band 1σ = VWAP - σ Upper Band 2σ = VWAP + 2σ Lower Band 2σ = VWAP - 2σ

📍 Pivot Points (5-Day Average)

mCube uses a 5-day averaged pivot formula for stability (less sensitive to single-day noise):

avg_high = mean(High[-5:]) avg_low = mean(Low[-5:]) avg_close = mean(Close[-5:]) Pivot = (avg_high + avg_low + avg_close) / 3 R1 = (2 x Pivot) - avg_low R2 = Pivot + (avg_high - avg_low) R3 = avg_high + 2 x (Pivot - avg_low) S1 = (2 x Pivot) - avg_high S2 = Pivot - (avg_high - avg_low) S3 = avg_low - 2 x (avg_high - Pivot)

📈 High Volume Node (HVN) Detection

Identifies price levels with concentrated institutional activity over 20 days:

# 1. Divide price range into 0.1% buckets bucket_width = avg_price x 0.001 # 2. Distribute each candle's volume across H-L range for candle in candles_20d: vol_per_unit = candle.volume / (candle.high - candle.low) for bucket in range(candle.low, candle.high): bucket.volume += vol_per_unit # 3. Score each bucket relative to average score = bucket.volume / avg_volume_across_all_buckets # 4. Return top N levels (default 3) as S/R levels

🕳️ Liquidity Gap (Vacuum Zone) Detection

Identifies thin-air zones where price moves quickly due to absence of resting orders:

# 1. Compute volume per 0.1% price bucket (same as HVN) # 2. Find contiguous bands where EVERY bucket < 10% of avg volume # 3. Calculate vacuum_score = avg_volume / max_bucket_vol_in_zone # Higher score = thinner zone = faster price movement through it # Output: [{low, high, vacuum_score}, ...] # Used by AdaptiveSLPlacer to avoid placing SL inside vacuums

💰 Max-Pain Calculation (Options)

Finds the strike price where total option holder pain is minimized (used on expiry days):

for each candidate_strike: total_pain = 0 for each strike in option_chain: # CE holders lose if spot settles above their strike if candidate > strike: total_pain += (candidate - strike) x ce_oi[strike] # PE holders lose if spot settles below their strike if candidate < strike: total_pain += (strike - candidate) x pe_oi[strike] max_pain_strike = argmin(total_pain)

🛡️ Fail-Safe Design Patterns

Every component in the monitoring and SR engine follows these fail-safe principles:

  • Never raise, always return safe defaults: All SR engine classes catch exceptions internally and return neutral results (no trigger, no SL change)
  • Monotonic SL tightening: SL can only move in the protective direction (higher for LONG, lower for SHORT). Prevents loosening on recalculation
  • Sticky session extremes: Session low/high track the absolute min/max of the day, never reset mid-day. Used for Condition B verification
  • Graceful degradation: If MTF data unavailable, engine uses base 8-source. If OI unavailable, uses pivot-only. If all fail, SL/target unchanged
  • Idempotent operations: Running the same monitor cycle twice produces the same result. No cumulative side effects
